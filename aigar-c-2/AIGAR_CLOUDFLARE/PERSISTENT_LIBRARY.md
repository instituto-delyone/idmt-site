# AIGAR persistent library storage\n\nCamada de persistência administrativa da biblioteca do AIGAR.\n\n## Arquitetura\n\nAdmin autenticado → POST /aigar/api/admin/upload → R2 original + D1 metadata → status uploaded → próxima etapa: processamento assíncrono → chunks de 25 páginas em R2 + metadados em D1.\n\n## Recursos necessários\n\nCrie um bucket R2 privado chamado `aigar-library`. Crie um D1 chamado `aigar-library` e aplique `schema.sql`.\n\nExemplo:\n\n```powershell\nnpx wrangler login\nnpx wrangler r2 bucket create aigar-library\nnpx wrangler d1 create aigar-library\nnpx wrangler d1 execute aigar-library --remote --file=aigar-c-2/AIGAR_CLOUDFLARE/schema.sql\n```\n\nVincule ao Worker `aigar-api` os bindings `AIGAR_LIBRARY_BUCKET` (R2) e `AIGAR_DB` (D1). O Worker responde `storage_not_configured` até ambos existirem.\n\n## API administrativa\n\n- `GET /admin/storage` — verifica R2/D1.\n- `POST /admin/upload` — exige Bearer de administrador validado pelo MedUnity; aceita PDF até 100 MB.\n- `GET /admin/documents` — lista os 100 documentos mais recentes.\n\n## Idempotência\n\nA interface calcula SHA-256 e envia `X-File-SHA256`. Se o hash já existir, o Worker retorna `already_exists`.\n\n## Segurança\n\nApenas `perfil=admin` acessa os endpoints; o PDF não é público; a senha não é armazenada pelo AIGAR; o arquivo original permanece no R2 privado.\n\n## Próxima etapa\n\nO status `uploaded` será consumido pelo processador de ingestão. A política seguirá o builder atual: texto original, sem resumo, chunks de 25 páginas e IDs determinísticos, com metadados persistentes no D1.\n
